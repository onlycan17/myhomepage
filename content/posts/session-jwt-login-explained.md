## 세 줄로 먼저 읽기

- 서버 세션은 **번호표를 서버의 기록과 대조하는 방식**, 서명된 JWT는 **출입증의 진위를 확인하는 데 쓸 수 있는 데이터 형식**이다.
- JWT의 서명은 위조 여부를 확인하기 위한 장치다. 내용 자체를 숨겨 주지는 않는다.
- 리프레시 토큰을 폐기해도 이미 발급한 액세스 토큰이 즉시 사라지는 것은 아니다.

## 로그인 한 번으로 여러 화면을 쓰는 이유

쇼핑몰에 로그인하고 장바구니로 이동할 때마다 비밀번호를 입력하지는 않는다. 서버는 다음 요청이 앞서 로그인한 사용자에게서 왔는지 구분할 단서를 사용한다. Notion의 「세션과 JWT」 메모를 바탕으로, 이 단서가 어떻게 관리되는지 정리해 봤다.

먼저 인증과 인가를 구분하면 이해가 쉽다. **인증은 누구인지 확인하는 일**, **인가는 그 사람이 무엇을 해도 되는지 확인하는 일**이다. 회사 출입증을 받았다고 모든 방에 들어갈 수 있는 것은 아니다. 로그인한 사용자라도 다른 사람의 주문을 볼 권한까지 생기지는 않는다.

## 세션: 번호표는 손님에게, 기록은 안내 데스크에

행사장 안내 데스크에 이름을 확인하고 입장했다고 가정하자. 직원은 임의의 번호가 적힌 표를 주고, 명부에 그 번호와 방문자를 연결해 둔다. 다시 들어올 때는 번호표를 명부와 대조한다.

서버 세션도 비슷하다. 로그인에 성공하면 서버가 추측하기 어려운 **세션 ID(로그인 기록을 찾는 번호)**를 발급한다. 브라우저는 이를 보통 쿠키에 보관해 요청할 때 보낸다. 서버는 저장된 기록을 찾아 사용자를 확인한다. 세션은 로그인뿐 아니라 로그인 전 방문 상태를 관리하는 데도 사용될 수 있다. [OWASP 세션 관리 문서](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

서버에서 그 기록을 무효화하면 이후 요청을 거절할 수 있다. 서버가 여러 대라면 서로 다른 안내 데스크가 같은 명부를 볼 수 있도록 기록 공유를 설계해야 한다. 이것이 세션을 사용할 때 고려할 운영상의 일이다.

## JWT: 필요한 정보와 위조 확인 장치를 함께 전달하기

이번에는 행사장에서 유효 기간과 입장 범위가 적힌 출입증을 받는다고 생각해 보자. 입구에서는 출입증이 믿을 만한 발급처에서 왔는지, 변조되지 않았는지 확인한다.

JWT는 정보를 담아 전달하는 형식이다. 이 글은 로그인 설명에서 자주 만나는 **서명된 JWT**를 다룬다. JWT 전체 규격에는 암호화된 형태도 있으므로, 모든 JWT가 아래 구조만 가진다는 뜻은 아니다.

`Header.Payload.Signature`

헤더에는 서명 방식 같은 정보, 페이로드에는 사용자 식별자나 만료 시각 같은 주장, 서명 부분에는 변조 여부를 검증하는 값이 들어간다. 흔히 사용하는 서명된 형태의 앞 두 부분은 Base64url로 표현된다. 이는 읽을 수 있게 되돌릴 수 있는 표현 방식이지, 비밀을 숨기는 암호화가 아니다. [OWASP JWT 문서](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)

출입증 비유의 한계도 기억해야 한다. 디지털 토큰은 복사될 수 있다. 유효한 토큰을 가진 사람이 실제 원래 사용자라는 보장은 없으며, 탈취한 토큰을 그대로 보내는 공격은 내용 위조와 다르다.

![세션은 브라우저의 번호표를 서버 기록과 대조하고, 서명된 JWT는 서버에서 서명과 사용 조건을 검증한다는 비교 도표](/blog/session-jwt-login-explained/session-vs-jwt.svg)

*그림 1. 두 방식의 확인 지점을 단순화했다. JWT를 쓰더라도 계정 상태나 권한 확인을 위해 저장소를 조회할 수 있다.*

## 무엇이 다른지 한눈에 보기

<div class="post-table-scroll" role="region" aria-label="서버 세션과 서명된 JWT 비교" tabindex="0">

| 비교 기준 | 서버 세션 | 서명된 JWT를 사용하는 방식 |
| --- | --- | --- |
| 확인 단서 | 세션 ID와 서버에 저장한 로그인 기록 | 토큰의 서명과 발급자·사용 대상·만료 등 조건 |
| 취소 방법 | 서버의 로그인 기록을 무효화 | 즉시 취소하려면 차단 목록이나 추가 상태 확인 등 별도 설계 필요 |
| 여러 서버 운영 | 세션 기록의 공유와 일관성 관리 | 검증 키의 배포·교체와 검증 정책 관리 |
| 정보 노출 | 번호표 자체에 개인정보를 담지 않도록 설계 | 서명만 한 페이로드에는 민감정보를 넣지 않음 |
| 공통 과제 | 번호표 탈취 방지와 요청별 권한 확인 | 토큰 탈취 방지와 요청별 권한 확인 |

</div>

“세션은 느리고 JWT는 빠르다”라고 단정할 수는 없다. 어떤 저장소를 쓰는지, 서명 검증 비용이 얼마인지, 요청마다 어떤 권한을 확인하는지에 따라 다르다. **세션은 상태를 관리하는 방식이고 JWT는 토큰 형식**이므로, 실제로는 둘을 함께 쓸 수도 있다.

## 출입증과 재발급권: 두 토큰을 나누는 이유

액세스 토큰은 서비스를 이용할 때 제시하는 증표다. 리프레시 토큰은 새 액세스 토큰을 발급받는 데 사용한다. 출입증과 재발급권을 나누는 셈이다. 둘 다 반드시 JWT여야 하는 것은 아니다.

<div class="post-table-scroll" role="region" aria-label="액세스 토큰과 리프레시 토큰 비교" tabindex="0">

| 구분 | 액세스 토큰 | 리프레시 토큰 |
| --- | --- | --- |
| 쓰는 곳 | 서비스를 제공하는 API | 토큰을 갱신하는 발급 서버 |
| 역할 | 허용된 범위에서 서비스 이용 | 새 액세스 토큰 요청 |
| 수명 설계 | 노출 피해를 줄이도록 짧게 정할 수 있음 | 로그인 유지 정책에 따라 설정 |
| 폐기 효과 | 서버가 폐기 사실을 검사하는 방식인지에 따라 다름 | 갱신 서버가 폐기를 확인하면 이후 재발급 차단 |

</div>

리프레시 토큰은 일반 서비스 요청에 매번 보내는 용도가 아니다. 갱신할 때 이전 토큰을 폐기하고 새 것으로 바꾸는 **로테이션(회전)**은 재사용을 탐지하는 방법 중 하나다. OAuth 보안 지침은 공개 클라이언트의 리프레시 토큰 재사용 탐지를 위해 회전 또는 송신자에 묶는 방식을 요구한다. 모든 앱에 단일 저장 위치나 만료 기간을 그대로 적용하라는 뜻은 아니다. [RFC 9700, 리프레시 토큰 보호](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)

## 로그아웃을 눌렀는데 토큰은 남을 수 있다

아래는 원리를 설명하기 위한 가상의 시간표다. **15분은 권장 설정값이 아니라 계산 예시**다. 서버는 액세스 JWT의 서명과 만료를 확인하되 별도 차단 목록은 조회하지 않는다고 가정한다.

1. 오후 2시에 만료 시각이 오후 2시 15분인 액세스 토큰을 발급한다.
2. 오후 2시 5분에 사용자가 로그아웃한다. 브라우저에서 토큰을 지우고 서버의 리프레시 토큰을 폐기한다.
3. 누군가 앞서 복사한 액세스 토큰을 가지고 있다면 오후 2시 15분 전까지 받아들여질 수 있다.

새 출입증을 발급하지 않는 것과 기존 출입증을 즉시 정지하는 것은 다르다. 즉시 차단이 필요하면 서버에서 폐기 목록이나 계정·세션 상태를 확인하는 등의 방법을 검토해야 한다. 그만큼 저장소 조회와 상태 관리가 다시 들어온다. [OWASP JWT 문서의 토큰 폐기 설명](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)

## 쿠키와 JWT는 양자택일이 아니다

쿠키는 브라우저가 정보를 보관하고 요청에 보내는 수단이다. 그 안에 세션 ID를 넣을 수도 있고 JWT를 넣을 수도 있다. JWT를 쿠키에 넣었다는 사실만으로 서버가 로그인 상태를 기억하는 방식이 되지는 않는다.

쿠키의 `HttpOnly`는 자바스크립트에서 쿠키를 직접 읽는 것을 막고, `Secure`는 HTTPS 연결에서만 보내도록 제한한다. `SameSite`는 다른 사이트에서 시작된 요청에 쿠키를 보낼 조건을 제한한다. 이 설정들이 모든 공격을 없애지는 않으며, 쿠키를 사용하는 인증에서는 CSRF(사용자의 브라우저를 이용해 원치 않는 요청을 보내는 공격) 대응도 함께 살펴야 한다. [OWASP 세션 쿠키 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#cookies)

개발 관점에서는 JWT를 읽어 사용자 이름이 보인다는 이유로 인증이 끝났다고 판단하면 안 된다. 신뢰할 키와 허용한 알고리즘으로 서명을 검증하고, 발급자와 사용 대상, 만료 등 서비스의 필수 조건을 확인해야 한다. 그 후에도 요청한 자원에 대한 권한을 별도로 확인한다. [RFC 8725, JWT 검증 지침](https://www.rfc-editor.org/rfc/rfc8725.html#section-3)

## 선택 전에 먼저 물어볼 것

어느 기술이 더 새로워 보이는지보다, **로그인 상태를 어디에서 관리하고 언제 끊어야 하는지**를 먼저 생각해 보자. 한 기기만 로그아웃해야 하는지, 권한 변경을 즉시 반영해야 하는지, 여러 서비스가 같은 증표를 검증해야 하는지가 선택의 기준이 된다.

세션의 번호표와 JWT의 출입증은 설명을 위한 출발점이다. 실제 로그인 품질은 발급 이후의 보관, 검증, 갱신, 폐기까지 이어지는 전체 흐름에서 결정된다.
