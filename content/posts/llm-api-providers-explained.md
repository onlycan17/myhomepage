## 세 줄로 먼저 읽기

- 모델은 답을 만드는 엔진이고, 제공업체는 그 엔진을 실행해 요청을 받는 곳이다.
- 호환 API는 요청 형식을 비슷하게 맞춘다는 뜻이다. 기능·비용·개인정보 처리까지 같다는 뜻은 아니다.
- 비교할 때는 같은 질문뿐 아니라 출력 조건과 실패·시간·비용도 함께 기록한다.

## 이름을 외우기 전에 역할부터 구분하기

Notion의 제공업체 비교와 API 실습 메모에는 여러 이름이 등장한다. 처음 접하면 모두 비슷한 AI 서비스로 보인다. 음식점으로 비유하면 요리법, 음식을 만드는 주방, 여러 식당을 연결하는 주문 앱이 섞여 있는 셈이다.

**모델**은 답을 생성하는 엔진이다. **제공업체**는 모델을 실행하고 요청에 응답하는 서비스를 제공한다. **실행 도구**는 모델을 내 컴퓨터나 서버에서 돌리도록 돕는다. 같은 모델 계열도 다른 제공업체에서 실행할 수 있으며, 설정과 배포 조건에 따라 결과가 달라질 수 있다.

| 실행 도구 | 모델 내려받기와 실행 지원 | Ollama에서 로컬 모델 실행 |

강의 자막에서 혼동하기 쉬웠던 **Groq와 Grok**도 구분해야 한다. Groq는 추론 서비스를 제공하는 회사이고, Grok은 xAI의 모델 이름이다. 알파벳 하나만 보고 같은 대상으로 처리하면 연결할 주소와 키가 달라진다. 이 표는 역할 구분용이며 현재의 제품 순위나 가격표가 아니다.

## API 키는 누구의 출입증일까?

API는 프로그램이 다른 프로그램에 요청을 보내는 통로다. API 키는 해당 서비스에 접근하는 자격을 나타내는 비밀 값이다. “어느 회사로 보낼지”와 “그 회사에 사용할 키”가 맞아야 한다.

원 메모에서 `.env`를 비밀 보관함에 비유했지만, 파일 자체가 자동으로 암호화되는 것은 아니다. 코드와 값을 분리하는 수단이다. 저장소에 올라가지 않도록 제외하고, 로그에 출력하지 않으며, 배포 환경에서는 그 환경의 비밀 관리 기능을 사용한다. 프런트엔드에 넣으면 방문자에게 노출될 수 있으므로 서버에서 관리해야 한다.

실습을 시작하기 위해 모든 회사에 가입할 필요는 없다. 사용할 한 곳 또는 로컬 모델부터 연결하고, 실제로 비교할 이유가 생기면 대상을 늘리면 된다. 키를 확인할 때도 값 자체 대신 “설정됨/없음” 정도만 표시하면 충분하다.

## OpenAI 호환이라는 말의 범위

공용 주문서가 있다고 생각해 보자. 식당마다 메뉴는 달라도 “메뉴 이름, 주문 내용” 칸을 비슷하게 받으면 주문 프로그램을 재사용하기 쉽다. OpenAI 호환 API도 일부 요청과 응답 형식을 맞춰 기존 클라이언트로 호출하기 쉽게 만든다.

아래는 **실행 코드가 아닌 교육용 의사코드**다. 역할을 보여 주기 위해 특정 업체의 현재 모델명이나 비밀 값을 넣지 않았다.

```text
연결 설정 = 제공업체 주소 + 해당 업체의 API 키
요청 = 그 업체에서 지원하는 모델 이름 + 질문 + 지원하는 옵션
응답 = 호출 결과
저장 = 모델 이름 + 답변 + 소요 시간 + 성공 또는 실패
```

호환이라고 해서 도구 호출, 이미지 입력, 구조화 출력, 추론 옵션을 모두 같은 방식으로 지원하지는 않는다. Ollama도 공식 문서에서 OpenAI API의 **일부**와 호환한다고 설명한다. 필요한 기능은 제공업체의 지원 목록과 실제 응답으로 확인해야 한다. [Ollama OpenAI 호환 문서](https://docs.ollama.com/api/openai-compatibility)

## 비교할 때 빠뜨리기 쉬운 조건

<div class="post-table-scroll" role="region" aria-label="모델 비교 실험 조건" tabindex="0">

| 기록할 것 | 왜 필요한가? |
| --- | --- |
| 질문과 참고 자료 | 모델마다 다른 시험을 보지 않기 위해 |
| 응답 길이·허용 시간 | 긴 답이나 긴 대기 시간이 무조건 유리해지지 않도록 |
| 모델 이름·제공업체·시점 | 어떤 조건의 결과였는지 다시 확인하기 위해 |
| 오류와 빈 응답 | 실패한 모델이 조용히 비교에서 빠지는 것을 막기 위해 |
| 사용량과 비용 | 답변 품질과 운영 부담을 함께 판단하기 위해 |

</div>

예를 들어 동네 행사 안내문을 세 모델에 맡긴다고 하자. 한 모델에는 날짜까지 주고 다른 모델에는 제목만 준다면 공정한 비교가 아니다. 조건을 같게 한 뒤 날짜 보존, 없는 정보 추가 여부, 읽기 쉬움 등을 따로 확인한다. 이 예시는 비교 방법을 설명하는 가상 상황이다.

원 강의의 한 질문에 대한 순위는 그 실습의 결과이지 시장 전체의 성능 순위가 아니다. 모델을 여러 개 연결했다고 자동으로 자율 에이전트가 되는 것도 아니다. 정해진 순서로 질문을 보내고 결과를 모으는 비교 프로그램일 수 있다.
