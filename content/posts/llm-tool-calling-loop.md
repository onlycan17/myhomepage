## 세 줄로 먼저 읽기

- 도구 정의는 사용 설명서이고, 도구 함수는 실제 일을 하는 코드다.
- 한 응답에 여러 도구 요청이 올 수도 있고, 결과를 본 뒤 새 요청이 이어질 수도 있다.
- “완료했습니다”라는 문장보다 도구의 실행 결과가 성공 판단의 근거다.

## 항공권을 조회한다면 누가 실제로 검색할까?

“파리행 비행기 가격을 알려 줘”라는 요청을 받았다고 하자. 모델은 항공권 조회 도구가 필요하다고 선택하고 목적지 같은 값을 담아 요청할 수 있다. 실제 항공편 정보를 가져오는 것은 연결된 프로그램이다.

모델이 함수를 호출하겠다고 응답하는 것과 그 함수가 실행된 것은 다른 사건이다. **도구 호출(tool calling)**은 모델이 정해진 형식으로 실행을 요청하는 과정이다. 애플리케이션은 요청을 확인하고 함수를 실행한 뒤 결과를 모델에 돌려준다. [OpenAI 도구 호출 가이드](https://developers.openai.com/api/docs/guides/function-calling)

![모델이 도구 요청을 만들면 프로그램이 허용 여부와 입력을 검사하고 실행 결과를 돌려주며, 추가 작업 또는 종료를 선택하는 흐름](/blog/llm-learning-series/tool-loop.svg)

## 도구 설명서를 건넨다고 기능이 생기지는 않는다

메뉴판에 “택배 배송”이라고 적었다고 배송 시스템이 생기지는 않는다. 도구 이름과 입력 형식을 정의해도 실제 동작하는 함수가 따로 있어야 한다.

<div class="post-table-scroll" role="region" aria-label="도구 호출 구성 요소 비교" tabindex="0">

| 구성 요소 | 쉬운 비유 | 역할 |
| --- | --- | --- |
| 도구 정의 | 업무 신청서 양식 | 이름·용도·입력 형식을 설명 |
| 모델의 호출 요청 | 작성된 신청서 | 사용할 도구와 인수를 제안 |
| 실행 코드 | 접수 담당자 | 권한·입력을 확인하고 허용된 함수를 실행 |
| 호출 ID | 접수번호 | 결과가 어느 요청의 답인지 연결 |
| 도구 결과 | 처리 결과서 | 성공·실패·조회 내용 등을 전달 |

</div>

모델이 낸 도구 이름으로 임의의 코드를 실행해서는 안 된다. 허용된 이름인지, 입력 형식이 맞는지, 현재 사용자가 할 수 있는 일인지 확인해야 한다. 형식에 맞는 요청이어도 권한이 없는 작업일 수 있다.

## 한 묶음과 여러 차례의 차이

원 메모는 첫 도구 요청 하나만 처리하는 방식에서 전체 목록을 처리하는 방식으로 확장한다. 여기에는 두 종류의 반복이 있다.

**목록 반복**은 한 응답에 담긴 여러 요청을 처리하는 일이다. **대화 반복**은 결과를 모델에 보여 준 뒤 새로운 요청이 필요한지 다시 확인하는 일이다. 첫 번째는 한 장의 주문서에 메뉴가 여러 개 있는 상황, 두 번째는 식사 후 추가 주문을 하는 상황으로 비유할 수 있다.

둘을 혼동하면 첫 요청만 처리하거나, 한 차례 실행 후 후속 작업을 놓치게 된다. 다만 목록에 여러 요청이 있다고 모두 동시에 실행해도 되는 것은 아니다. 순서가 필요하거나 같은 데이터를 바꾸는 작업은 의존 관계를 확인해야 한다.

## 무한 반복 대신 멈출 조건 넣기

아래는 **실행 가능한 SDK 코드가 아닌 교육용 의사코드**다. 원 메모의 반복 구조에 횟수와 실패 처리 경계를 더해 설명했다.

```text
정한 횟수·시간·비용 한도 안에서 반복:
  모델 응답을 받는다
  도구 요청이 없으면 최종 답변을 반환하고 종료한다
  각 요청의 도구 이름·입력·권한을 확인한다
  허용된 작업만 실행하고 성공·실패 결과를 기록한다
  요청과 결과를 같은 호출 ID로 연결해 모델에 전달한다
한도에 도달하면 미완료 상태와 다음 확인 사항을 반환한다
```

모델이 더 이상 도구를 요청하지 않는다고 모든 목표가 실제 달성됐다는 뜻도 아니다. 필요한 기록이 생성됐는지처럼 시스템이 확인할 수 있는 완료 조건이 있어야 한다.

## 저장 요청이 시간 초과됐다면?

다음은 가상 사례다. 연락 요청을 저장하는 도구가 시간 초과됐다. 화면에는 실패처럼 보이지만 서버에는 이미 저장됐을 수도 있다. 같은 요청을 그대로 재실행하면 두 번 저장될 수 있다.

<div class="post-table-scroll" role="region" aria-label="도구 실행 상태별 처리" tabindex="0">

| 확인된 상태 | 사용자에게 알릴 내용 | 다음 처리 |
| --- | --- | --- |
| 저장 성공 | 저장이 확인됐다 | 결과를 근거로 완료 응답 |
| 실행 전 거절 | 저장되지 않았다 | 입력·권한 문제 안내 |
| 결과 불명 | 저장 여부를 확인 중이다 | 기록 조회나 중복 방지 식별자로 확인 |

</div>

이처럼 “에러가 났으니 아무 일도 안 일어났다”는 가정을 피해야 한다. 재시도해도 같은 작업이 중복되지 않도록 설계하는 것을 **멱등성**이라고 한다. 조회와 저장은 실패 후 처리 방식이 다를 수 있다.

## 자율성은 허용된 선택의 범위다

도구를 선택하는 모습을 사람의 의지와 같은 것으로 볼 필요는 없다. 시스템이 보여 준 상황과 도구, 허용한 권한 안에서 다음 행동을 고르는 것이다. 좋은 에이전트는 도구가 많은 시스템보다, 결과를 확인하고 실패와 종료를 설명할 수 있는 시스템에 가깝다.
